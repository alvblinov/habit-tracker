# Implement

Доведи один подтверждённый план до проверяемого результата. Главный агент —
координатор; исходники и тесты изменяют назначенные субагенты.

## Вход и начало

- Пользователь передаёт `plan_path` и подтверждает выполнение плана.
- Прочитай `AGENTS.md`, `GOAL.md`, `STATUS.md`, `README.md` и план.
  Проверь, что план содержит границы задачи и критерии приёмки.
- Выполняй скилл после выхода из Plan mode. Если сейчас разрешено только
  планирование, остановись и попроси перейти к выполнению.
- Убедись, что открыт нужный проект, есть первый коммит и доступны роли
  `demo-implementer`, `demo-test-writer`, `demo-test-runner`, `demo-auditor`.
  Если роль недоступна, верни BLOCKED; не изображай её запуск обычным ответом.
- Зафиксируй `base_ref` как текущий HEAD и начальный Git status, включая новые файлы.
  Согласованный план может быть незакоммичен. При посторонних изменениях,
  пересекающихся с задачей, остановись для уточнения; ничего не откатывай.
- Создай новую папку прогона, например `reports/001-core/01/`.
  Существующие отчёты не перезаписывай. Это `run_dir`.

## Одна последовательная цепочка

Все агенты работают в одной папке и ветке проекта. Не создавай отдельные worktree.
Запускай следующую роль только после завершения предыдущей: она использует её файлы.
Передавай каждой роли `plan_path`, `run_dir`, `base_ref`, цель и ограничения,
а не весь диалог интервью. Дополнительные файлы пусть читает по необходимости.

1. **demo-implementer** — реализует план, пишет `implementation.md`.
   Дождись IMPLEMENTED. При BLOCKED остановись.
2. **demo-test-writer** — пишет тесты, пишет `tests.md`.
   Дождись WRITTEN. При BLOCKED остановись.
3. **demo-test-runner** — выполняет тесты и сборку, пишет `validation.md`.
   Дождись фактического результата. Не исправляй код параллельно с запуском.
4. **demo-auditor** — проверяет план, изменения и результаты; пишет `audit.md`.
   Запусти его и при FAILED/BLOCKED runner, чтобы получить сводку проблемы,
   если отчёт runner существует. Отсутствие проверки не допускает PASS.

После каждого этапа коротко сообщай, кто работал и какой файл появился.
В `STATUS.md` обновляй только факты: текущую фазу, ссылки на план/отчёты и блокеры.
Завершённого субагента освобождай штатным способом, если это нужно для лимита
одновременно открытых агентов. Не запускай больше одного работника одновременно.

## Исправления и завершение

- При FIX предложи конкретное исправление в рамках согласованных требований.
  Допустим **один** дополнительный цикл исправления без изменения объёма задачи.
  Создай следующую папку попытки, например `reports/001-core/02/`, передай
  implementer предыдущий audit и снова пройди четыре роли.
- Test-writer в повторном цикле сохраняет полезные тесты и добавляет
  регрессионный тест, если он нужен. Runner обязательно запускает всё заново.
- При BLOCKED, необходимости менять требования, зависимости или права,
  либо повторном FIX остановись и сообщи, какое решение требуется.
- Только при свежих runner PASSED и auditor PASS запиши в STATUS:
  «проверено, ожидает ручной приёмки и коммита».
  Не объявляй выполненные команды доказательством всех возможных свойств продукта.
- В финале дай краткое резюме изменения, результаты проверок, ограничения
  и путь к `audit.md`. Предложи сценарий ручной проверки в браузере.

Commit, push, создание репозитория и публикация не входят в скилл.
В демо их выполняет ведущий в VS Code после просмотра изменений.
Главный агент не подменяет четыре роли собственной реализацией.
